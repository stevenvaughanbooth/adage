# Demo sandbox — specification

A small, realistic repository — **acme-billing** — with conventions a coding agent cannot guess and
must otherwise discover. Real headless Claude Code agents work tasks in fresh copies of it, with
and without Adage.

## Constraints

- **Python 3.9 standard library only.** No pip installs. Tests use `unittest`. The system
  `python3` is 3.9.6; there is no `pytest`.
- Everything is generated by `demo/sandbox/generate.py <out_dir>`, deterministic, and fast
  (< 1 s). The generated directory is a git repository with one initial commit.
- Every script is harmless: reads and writes only inside the sandbox.

## The three conventions

1. **Work items live only in the tracker.** `scripts/wi-lookup <ID> [--json]` prints the work item
   from `.tracker/items.json`: `id`, `title`, `description`, `linked_files`, `acceptance`. Task
   prompts name only the ID ("Pick up W-2042 and get it done."). The README says only that work items
   are in "the internal tracker".
2. **Tests run through make.** `make test` sets `ACME_ENV=test` and runs
   `python3 -m unittest discover -s tests`. Running unittest directly fails immediately from
   `tests/__init__.py` with: `RuntimeError: ACME_ENV is not set — run tests with 'make test'`.
   (`pytest` is simply not installed.) This is the **dead end**.
3. **Generated models.** `schema/*.json` define records (fields with type and default).
   `make gen` runs `tools/gen.py`, which writes `acme/generated/models.py` (dataclasses). The
   generated file is committed. `make ci` runs a staleness check (regenerate to a temp file and
   compare) and fails with `generated models are stale — run 'make gen'` if they differ. Changing a
   schema without `make gen` breaks CI. This is the **finish-line obligation**.

## Layout

```text
acme-billing/
├── README.md              two short paragraphs; mentions "the internal tracker" and the Makefile
├── Makefile               gen · test · ci · lint (lint = python3 -m py_compile over acme/)
├── scripts/wi-lookup      executable Python
├── .tracker/items.json    all work items (training + held-out)
├── schema/invoice.json    fields: id, customer_id, amount_cents, tax_region, discount_pct, …
├── schema/customer.json   fields: id, name, email, region, …
├── tools/gen.py           schema → dataclasses
├── acme/__init__.py
├── acme/billing.py        totals, tax by region, discounts, late fees
├── acme/customers.py      validation, lookup helpers
├── acme/generated/__init__.py
├── acme/generated/models.py
└── tests/
    ├── __init__.py        the ACME_ENV guard
    ├── test_billing.py
    └── test_customers.py
```

## Work items

Twelve items, each with a **hidden check**: an extra `unittest` file kept outside the sandbox
(`demo/sandbox/hidden/test_<ID>.py`) and copied in only when scoring. Seeded bugs are real, small,
and located in the linked files. Mix per split:

| Split | IDs | Kinds |
| --- | --- | --- |
| Training | W-1041 … W-1046 | 4 code fixes (billing/customers), 2 schema changes that require `make gen` |
| Held-out | W-2041 … W-2046 | 4 code fixes, 2 schema changes — different bugs and fields from training |

Examples of the kind of work:

- Discount rounding uses floor instead of banker's rounding for half-cents.
- EU tax region uses the wrong rate.
- Late fee applied on the due date instead of after it.
- Email validation accepts addresses without a domain dot.
- Add `currency` (string, default "USD") to the invoice schema and use it in `format_invoice`.
- Add `due_days` (int, default 30) to the invoice schema and use it in `due_date`.

Each work item's `description` states the problem as a user would. `linked_files` lists the one or
two files that need to change. `acceptance` states the expected behaviour precisely enough that the
hidden test is fair.

## Scoring

`demo/sandbox/score.py <sandbox_dir> <ID>`:

1. Copies `hidden/test_<ID>.py` into `tests/`.
2. Runs `make ci` (staleness check + all tests, including the hidden one).
3. Prints JSON: `{"id", "passed": bool, "stale_generated": bool, "tests_run", "failures", "errors"}`.

A task **succeeds** only if `make ci` passes: the hidden test passes, no existing test breaks, and
generated models are fresh.

## Self-check

`demo/sandbox/selfcheck.py` verifies that every held-out and training item:
- fails its hidden test on the untouched sandbox, and
- passes after applying a reference solution (`demo/sandbox/solutions/<ID>.patch` or a Python
  function that edits the files), including `make gen` where required.

It also verifies the dead end (direct unittest fails with the guard message) and the obligation
(schema change without gen → `make ci` fails with the stale message).

## Arms and metrics (chunk E1)

`demo/run.py` runs any of five arms (`docs/claude-mod/architecture.md` §9,
`docs/claude-mod/test-plan.md` §7.2). The wiring of each is one row of `ARMS` in `run.py` and is
unit-tested (`demo/test_run_arms.py`).

| Arm | Hooks | Environment | Purpose |
| --- | --- | --- | --- |
| `a0` | none: no `--settings`, no plugin | no `ADAGE_*` variable at all | the registered protocol's no-hooks baseline |
| `control` | `--settings` from `adage hooks-config` | `ADAGE_ARM=control` | computes what it would say and logs it, says nothing; the in-product savings baseline, not `a0` |
| `adage` | the same | `ADAGE_ARM=treated` | today's product |
| `mod-observe` | the plugin only: `--plugin-dir`, never `--settings` from `hooks-config` | `ADAGE_ARM=treated`, `ADAGE_MOD_OBSERVE=1` | proves the mod's observation changes nothing |
| `mod` | the plugin only | `ADAGE_ARM=treated` | the design |

Every arm also gets `ADAGE_HOME=$DEMO_ROOT/adage-home` and `ADAGE_AUTO_LEARN=0` (except `a0`),
`--setting-sources project,local` (so no plugin or hook from the person's own settings loads),
`--debug --debug-file runs/<id>/claude-debug.log` and `--include-partial-messages`. stderr goes to
`runs/<id>/stderr.log`; stdin is empty.

**One session per run.** Every run passes its own `--session-id <uuid4>`, and no arm inherits the
variables of a Claude Code session the runner itself runs in (`CLAUDECODE`, any `*SESSION_ID*`,
`CLAUDE_CODE_REMOTE*`, `CLAUDE_CODE_MESSAGING_*`, `CLAUDE_CODE_ENTRYPOINT`,
`CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_PID`; the rule of `evals/live/runner.py`). A child that
inherits `CLAUDE_CODE_SESSION_ID` takes that id as its own: every run then shares one transcript
name and one spool, `learn` reads one foreign transcript, and `hooks_wired_once` counts every
session's `session_start` in one file. `learn` refuses runs that share a session id. Transcripts
are found under `$CLAUDE_CONFIG_DIR/projects` (else `~/.claude/projects`), in the sandbox's own
project directory; set `CLAUDE_CONFIG_DIR` to a directory of the demo root to keep the plugin's data
directory (below) to this run.

**The mod under `--plugin-dir`.** The mod finds its hook binary at `<plugin data>/bin/hook`, the
directory read from `CLAUDE_PLUGIN_DATA` in the engine's environment or derived from an installed
plugin's root. Claude Code gives a `--plugin-dir` plugin `<config dir>/plugins/data/<name>-inline`
but passes it to command hooks only, so the plugin arms set `CLAUDE_PLUGIN_DATA` to that directory
in the session's environment; without it the mod stays inert (no `TurnStep` is asked) while the
command hooks run.

Smoke runs (`run.py one`) are recorded with phase `smoke`, never `eval`: `report.py` compares only
the interleaved `eval` runs.

**The plugin's binaries.** One plugin ships both binaries (plan A8). `plugin/build.sh` builds
release binaries and stages `plugin/claude-code/dist/<host triple>/adage` and `adage-exec` with
`dist/SHA256SUMS`; the plugin's `scripts/session-start` links `${CLAUDE_PLUGIN_DATA}/bin/adage`
and `bin/adage-exec` to those copies after checking their digests (else to `adage` and
`adage-exec` on `PATH`), and links `bin/hook`, which every other hook runs, to `adage-exec` while
`$ADAGE_HOME/exec/enabled` exists and to `adage` otherwise. A predict grant answers a `TurnStep`
only through `adage-exec`, so the `mod` arm predicts only with that marker in the shared
`ADAGE_HOME`. The runner stages the same way without writing to `plugin/`: it copies the plugin
(default `plugin/claude-code`, `--plugin-dir`) to `$DEMO_ROOT/plugins/<name>/`, leaving any
`dist/` behind, and stages `adage` (default `ADAGE_BIN`, else `target/release/adage`;
`--plugin-bin`) and `adage-exec` (default `ADAGE_EXEC_BIN`, else the `adage-exec` beside that
`adage`, when there is one) as `dist/<target>/…` with their `SHA256SUMS` lines. `--no-stage` loads
`--plugin-dir` as it is, for a plugin `plugin/build.sh` already staged. Nothing is downloaded.

**Keys recorded per run** (`metrics` in `state.json`), beside the earlier ones:

| Key | Meaning |
| --- | --- |
| `requests` | `[DEBUG] [API REQUEST]` dispatch lines in the debug log, counted with the regex of `evals/reflex-proof/harness/heldout_analysis.py` (retries count) |
| `requests_verified` | the harness's cross-check: dispatch ids unique, and the stream's distinct explicit request ids (`request_id`/`requestId` fields, never message ids) equal the dispatches of the session's own turns (`source=sdk`, or `repl_main_thread`), or their surplus is explained by `[ERROR] API error (attempt …)` lines. Dispatches of other sources (Claude Code 2.1.29x in a remote session: `generate_session_title`, `side_query`) are counted in `requests` and never streamed. `report.py` treats an unverified count as missing |
| `requests_check` | `stream_request_ids`, `api_error_entries`, `cross_check` (exact equality), `requests_streamed` (dispatches of the session's own turns), `requests_by_source` |
| `session_id`, `session_id_as_asked`, `transcript` | the session's id (the stream's; whether it is the `--session-id` passed) and its transcript |
| `passed`, `ci_passed`, `hidden_passed`, `hidden_tests_run`, `stale_generated`, `ci_tail`, `hidden_tail` | `score.py`'s keys, all recorded |
| `dead_end_hits` | dead ends hit (a verification that failed), as before |
| `dead_end` | `{"hit", "substituted"}`; `substituted` (also `dead_end_substituted`) counts spool records of a dead end replaced before it ran (a `substituted` judgement, or a `pretool` record saying so; never a withheld one) |
| `predicted_steps` | spool `turn_step` records with `predicted`/`predict` set |
| `receipts_as_results` | spool `pretool` records with `answered: receipt` |
| `directives` | directives delivered, from the spool's decisions (`would_have` is not delivered); with no spool, the `<adage-reflex` blocks in the stream's hook responses (`directives_in_stream`) |
| `subagent_tool_calls` | tool calls in assistant messages with a `parent_tool_use_id` |
| `session_starts`, `spool_exists`, `hooks_wired_once` | T-E1-02: `a0` writes no spool; every hook arm exactly one `session_start` record |

Spool metrics fail soft: a record of an unknown shape counts as nothing. `demo/report.py`
compares any two arms (`--a mod --b a0`; `compare(runs, a="mod", b="a0")`) with the task-stratified
permutation p and the task bootstrap interval; `requests` joins the Holm family, the mechanism
counts (`predicted_steps`, `receipts_as_results`, `dead_end_substituted`, `directives`,
`subagent_tool_calls`) are reported unadjusted.

**The identity check** (T-E1-03): `demo/replay_hooks.py` feeds a recorded stream of hook payloads
(`demo/fixtures/hook-stream.jsonl`) to `adage hook claude <event>` with and without
`ADAGE_MOD_OBSERVE=1`, records each event's stdout and spool records, and diffs them
(`--identity`, or `--compare` for two recordings).

**Live runs need an API key** (`ANTHROPIC_API_KEY` or a logged-in `claude`) and cost money; the
five arms' first live run (Claude Code 2.1.292) is in `docs/claude-mod/evaluation-results.md`.
Everything else is unit-tested offline: `cargo xtask test python demo`.
