How we tested

Fewer model calls. The same correct code. Here is exactly how we checked.

Your coding agent spends model calls re-exploring your repository and re-checking work it has already checked. Adage learns the work your repository repeats and handles the predictable steps on your CPU, so the agent spends its calls on the actual problem.

The question every study asks

Can Adage handle predictable steps on your CPU so the agent needs fewer model calls, without hurting correctness?

It is strongest on recurring task patterns in a repository it has learned. A novel task still needs the model's reasoning, and Adage leaves that alone.

How we test fairly

Same task, with and without. Rules first, results after.

A tool that saves calls by cutting corners is easy to build. These six rules are how we make sure Adage does not.

  1. 01

    Paired comparisons

    Every task runs as a paired comparison, with Adage and without it: same repository, same prompt, a fresh checkout each time. Comparing pairs keeps a hard task from looking like a slow tool.

  2. 02

    Hidden tests

    The agent never sees the tests that grade its work. Fewer calls only count if the code is still right.

  3. 03

    Safety controls

    Before any comparison, runs where checking again is the right move: a failing test, a later edit, a changed config, a broader change, an explicit request to rerun. Adage must never let the agent skip necessary work. One miss stops the study.

  4. 04

    A person approves, a sandbox runs

    Adage runs only the exact command a person approved, inside an operating-system sandbox, on the CPU. If the command or its environment changes, the approval stops matching and nothing runs.

  5. 05

    Pass rules written first

    The line a result must clear is written down and committed before the first session, and never moved after. Revisions are dated and come before the runs they affect.

  6. 06

    Every attempt kept

    Failures, invalid runs and aborted studies stay in the record with their costs. Nothing is rerun to get a better number.

What “held-out” means

We improved Adage on a development task, so a good score there proves little. Held-out tasks are new tasks, written and frozen before any result was read, and never used for tuning. They answer the real question: does it work on the next task, the one nobody tuned for?

More detail: how a session is counted

Model requests are counted from Claude Code's own debug log: one line per request it sends, retries included, since they are billed too. Each session is cross-checked against the request ids in its output stream; a gap that logged API errors do not explain makes the session unverified, and its whole paired block leaves the comparison, for every arm alike.

The headline test is the ratio of total requests, Adage over alone, across the paired blocks. Its one-sided 95% upper bound comes from a bootstrap that resamples blocks within each task, 20,000 draws, with a fixed seed. Quality must not fall: Adage's hidden-test passes must be at least the agent alone's, minus one.

Censoring works against Adage. A session that stops early (its turn limit, its budget, the clock) is a quality failure in every arm, and only Adage's is raised to 60 requests. Two sensitivity analyses run alongside: without censored blocks, and without the task closest to anything in training.

Arms. The held-out study has three: the agent alone; Adage's hooks and card with no approved check; and Adage with the approved check. The middle one shows how much comes from advice alone. Every model is Claude Haiku 4.5; cost is the API list price.

What changed to get there

Verification ownership

Adage now owns the check a person approved. At the start of the session it tells the agent which command it runs and when. After matching edits it runs it on the CPU and hands back a receipt naming the agent's own new tests. When the agent finishes, it runs it again if the code changed. The agent stops re-checking because the check is visibly done.

The orientation card

The procedure card used to show an example to copy, and agents went paging through files to imitate it. Now it says where each file stands right now: line counts, the last definitions, the end of the test file, the changelog's head. Adage reads them itself, read-only, in under 1,200 tokens.

Limits and what's next

What this does not show yet, and what we test next.

What we have not shown

  • One repository, one model. Every launch study used Marshmallow and Claude Haiku 4.5. Other repositories and other models are untested.
  • A guided start. The routine Adage runs was learned from ten guided sessions. Fifteen unguided sessions have not produced one yet.
  • Model calls, not GPUs. We count model requests, tokens and API cost. GPU use and energy are not measured.
  • Repeating work only. The gain comes from work a repository repeats. A novel task still needs the model's reasoning.

What we test next

  • Expensive to cheap. Learn from sessions with a strong model, then see whether a cheaper model, with Adage, can do the same work.
  • More repositories. Including one the learning pipeline has never seen.
  • Learning without guidance. Executable routines from ordinary, unguided sessions.

More detail: the held-out commands

From evals/reflex-proof/harness, with $H the frozen held-out root. live is the only paid step; it dispatches in the frozen order, controls first, and stops on any lapse. The handoff has the full sequence.

python3 heldout_cohort.py prepare $H        # offline: fresh checkouts, read-only runtime
python3 heldout_cohort.py verify-grants $H  # a person issued exactly the reviewed approvals
python3 heldout_cohort.py live $H           # paid: 65 sessions, one at a time
python3 heldout_cohort.py report $H         # the registered analysis and its decision record
